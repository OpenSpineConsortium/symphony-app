1. A token pasted while the page still checks the stored sign-in: the panel opens as the stored
   account, then acts with the pasted token under that name, writes included (S4)

   Severity: medium-low. The window is rare: a paste during the page's first question, and a
   paste check slower than that question. But when it is hit, a write is made as another account
   than the page names, and with one more GitHub hiccup the wrong name stays for good.
   Status: left open. 0b9600b fails the same way in both configurations. It contradicts this
   round's claim that "a call goes out only with a token the page has named".

   Mechanism: storeSignin() clears shownLogin and shownToken, which turns ready()'s rule off.
   That rule asks for naming only when shownToken is set or the call writes for a named account,
   and gh() takes account = shownLogin = ''. The paste handler leaves the panel open, and cp-who
   still names the stored account.

   Sequence:
   1. The browser keeps a sign-in for tester (configured: a sign-in record; unconfigured: a kept
      paste). The person opens /symphony/control/?repo=acme/demo.
   2. While the box stands and the page asks GitHub whose the kept token is (1.5 s), they paste
      another account's token, github_pat_OTHER, Keep unticked, and press Open the panel. The
      check of the paste takes 2 s.
   3. GitHub answers about the kept token first. enter() opens the panel ("Signed in as tester
      through GitHub, kept on this browser.") and the load starts.
   4. The paste's check comes back. storeSignin() keeps it for the tab, token = github_pat_OTHER,
      and a second enter() asks GitHub about it. The panel stays open, naming tester.
   5. The person presses "Run the workers now" (visible and enabled).

   Observed (s4.log; s4.unconfigured.log the same):
   - cp-who named tester from 1685 ms to 4910 ms, then "Signed in as other-person with a token,
     for this tab."
   - Pressed at 2410 ms: "2423 POST /repos/acme/demo/actions/workflows/workers.yml/dispatches
     Bearer github_pat_OTHER", and GET /repos/acme/demo/issues at 2946 with the paste, while the
     page named tester.
   - Second variant, GitHub answering the paste's second GET /user with 502:
     - the write went out at 2600 ms with github_pat_OTHER;
     - cp-who still names tester at the end;
     - a Refresh sends all seven reads with github_pat_OTHER, for good.
   - 0b9600b (s4.base.log, s4.base.unconfigured.log): the same, with the write at 2470 ms and at
     2449 ms.
   - e2e2's H5 covers the other order (the paste's check back first) and passes.

   Script: s4.test.mjs (two variants; it presses only a button that is visible).

   Smallest fix (fix-paste.json, tested in both configurations): in wireGate's paste handler,
   just before storeSignin(KEY_TOKEN, t, keep), add
       showGate(); state = emptyState(state.repo);
   The panel the stored sign-in opened closes, with its name and its reads, until GitHub names
   the paste. In the 502 variant the page then opens naming nobody, as enter() promises.

2. One GET /user that GitHub never answers holds every later call of the tab, or holds the
   sign-in box, with no words and nothing to press that helps (S1, S2, S2c, S3)

   Severity: low-medium. Nothing goes wrong at GitHub, but the tab sits on "Reading..." or on
   the box with no message until it is reloaded. It needs one request that never comes back
   (a dropped connection, a captive portal).
   Status: introduced. 0b9600b passes all four.

   Mechanism:
   - whoAmI() shares one question per token (naming), and the question has no time limit.
   - Since this round, every call with a token the page has not named waits on that question:
     ready() -> named() -> whoAmI().
   - A second press asks nothing new, because the token is the same and so is the promise.
   - A re-paste of the same token shares it too, since storeSignin() does not clear naming.
   - The paste handler's say('') leaves the box with no words.

   Sequences and observations:
   - S1 (configured; s1.log): the kept sign-in reaches its last minute. Refresh renews it
     (ghu_NEW), and the GET /user about ghu_NEW (2062 ms) never answers.
     - 24 s later: still "Reading acme/demo...", no message, cp-who naming tester.
     - A second Refresh sent nothing in 6 s.
     - 0b9600b (s1.base.log) loaded at once with ghu_NEW, and again on the second Refresh.
   - S2 (both configurations; s1.log, s1.unconfigured.log): paste github_pat_NEW.
     - The check answers, then enter()'s GET /user never answers: the box, no words.
     - The person presses again with the same token. The check (third /user) answers, and no
       fourth is sent.
     - 12 s later: still the box, empty message.
     - 0b9600b: four /user calls, and the panel opens.
   - S2c (both configurations; w1.log, w1.unconfigured.log): the same on /symphony/cost.html.
     - Three /user calls; the box with no words 10 s after the second press.
     - 0b9600b opens the page and reads METRICS.json.
   - S3 (both configurations): tab 1 is open on the kept sign-in, and tab 2 keeps a new token of
     the same account (github_pat_NEW).
     - Tab 1's question about it, from the storage event, never answers.
     - Refresh in tab 1 sends nothing for 24 s: "Reading acme/demo...", no message.
     - 0b9600b read at once, with the token unnamed (the previous round's finding).

   Script: s1.test.mjs (S1, S2, S3) and w1.test.mjs (S2c).

   Smallest fix (fix-stall.json, two pairs, tested in both configurations):
   (a) In call(), give a GET /user AbortSignal.timeout(20000), as checkToken() and exchange() have,
       and turn a TimeoutError into "GitHub did not say within 20 seconds whose the token is;
       press again."
   (b) In storeSignin(), set naming = null beside shownLogin and shownToken, so a paste asks
       afresh.

5. Forget's words are replaced by the failure of an action that was on its way (F1, F2)

   Severity: low (words only). It drops what Forget said: that another tab signed in for itself
   keeps its sign-in, and, in the unconfigured page, that the personal access token stays valid
   at GitHub. Nothing is sent: this round's `ended` holds the write back.
   Status:
   - F1 without Web Locks: introduced. The 22 s wait of finding 3 makes Forget pressable;
     0b9600b signs out at once.
   - F1 with a lock: left open. 0b9600b does the same.
   - F2: introduced. It is a side effect of this round's naming wait; on 0b9600b the write went
     out at once with the unnamed token, before Forget.

   Mechanism: endHere() promises that what is still on its way "is dropped when it comes, not
   shown or said". Loads keep that promise through stale(s). Actions do not: their catches say
   e.message. refusedToken() now returns false at once for a tab already signed out ("has said
   why"), yet call() still throws the 401 failure.

   Sequences and observations:
   - F1, no lock (f1.log):
     - A kept sign-in; GitHub refuses the write "Run the workers now".
     - The person presses Forget 2 s later. Its revoke words appear.
     - Within 500 ms they are replaced by "GitHub refused the sign-in's token (401): it was
       revoked or has run out. Press Sign in with GitHub again."
   - F1, with a lock: the dispatch's 401 comes back 1.5 s after the press, just after Forget's
     revoke (Forget at 300 ms). The same replacement; f1.base.log shows 0b9600b does it too.
   - F2 (both configurations; f2.log, f2.unconfigured.log): another tab puts a new token of the
     same account in place.
     - While this tab asks GitHub about it (2 s), the person presses "Run the workers now", then
       Forget.
     - No write goes out, which is right.
     - Then "This page is signed out now: the token was forgotten, or GitHub refused it, here or
       in another tab. Sign in again to go on." replaces Forget's words. In the unconfigured page
       those words included "The personal access token itself stays valid at GitHub until it
       runs out or you delete it at github.com/settings/personal-access-tokens."
     - 0b9600b (f2.base*.log): the write went out at once with the new token, before Forget.

   Script: f1.test.mjs (two variants, configured) and f2.test.mjs.

   Smallest fix (fix-ends.json, four pairs, tested; F1 and F2 pass in both configurations):
   - Count sign-outs: var ends = 0, and ends++ in endHere().
   - Capture era = ends in call().
   - End call()'s chain with
       .catch(function (e) { if (ends !== era) return new Promise(function () {}); throw e; })
   Every endHere() comes with words of its own (Forget, refusedToken, expired, lookAtStorage),

   - Narrower alternative for F1 alone (fix-drop.json, tested): refusedToken() returns null for a
     tab already signed out, and call() drops on null.
   - Either way a dropped question leaves `naming` set for its token. Ship it with fix-stall's

   Observed (w1.log, w1.unconfigured.log): "Another tab of this browser kept a new token in place
   of the one this page had, and GitHub could not be asked whose it is (GitHub answered 502:
   Server Error.)." 0b9600b keeps "GitHub answered 502: Server Error.".

   Script: w1.test.mjs (W1).

   Smallest fix (fix-words.json, tested): in followToken(), note `var changed = now !== token;`
   before `token = now;`, and in the catch, after clearing cp-who, `if (!changed && !known)
   return;`. H4, H4b, H11 and G4 still pass.

THEORIES, NOT REPRODUCED
------------------------

Each was reasoned through but not run, or would need a contrived timing.

- A false "Now signed in as X, not Y: another tab ...". It needs a write waiting in named() across
  a Forget and a paste in the same tab, with the paste's check done before one GitHub /user
  answers. named() keeps `before`, and storeSignin() cannot clear it.
- A page that opened unnamed (any non-401 failure of its first /user) never asks again on its
  own. Until a reload its calls and writes go out unnamed, including after its own renewal or a
  token taken up from another tab. There, followToken's warning is the only word. This is by the
  rule as written (enter() opens such a page on purpose), but it means "only with a token the
  page has named" is not the whole truth.
- Browsers without AbortSignal.timeout (Chrome before 103, Firefox before 100, Safari before 16):
  exchange() and checkToken() have no time limit. A hung service then holds the renewal lock for
  good, and since this round every sign-in's 401 waits on that lock.
- "The sign-in changed while this was on its way" is said even when the change came before the
  press: the storage event is looked at only 300 ms later.
- signOut() names one deletion page (tokens or personal-access-tokens) when this tab's paste and
  the kept paste are of different kinds. It reads only the first.
- A token no request can carry, taken up mid-session from a tab of an older version, would leave
  the panel open. followToken's words would carry the paste advice in parentheses, with no box to
  paste into. This only happens during a deploy.
- W1's words could also follow from another tab keeping the very token this unnamed page holds
  (a re-paste of the same token). fix-words covers it too.
- Before this round, and not counted as findings:
  - Merge stays armed after "The sign-in changed" (by design).
  - signOut's revoke-failure branch omits "The repositories you listed stay.".
  - The cost page's measured() is not stale-guarded, so a quick second choice of repository can
    show the first one's answer.
