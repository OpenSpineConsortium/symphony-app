THEORIES (NOT REPRODUCED)
-------------------------

T1. Back/forward cache.
    - Claim: a page restored from the bfcache gets none of the storage events it missed. Its next
      call takes up whatever is stored (ensureToken), and the handler never runs. So it can act as
      another account under the old name, as in finding 2, or show a panel for a sign-in forgotten
      elsewhere until its next call.
    - Why not reproduced: headless Chromium reports BackForwardCacheDisabledForDelegate, even with
      --disable-back-forward-cache taken out of its arguments. The full Chrome channel was not
      launched, because it reaches Google's servers.
    - Fix: a pageshow listener that, when event.persisted is true, runs the handler's look at once.

T2. A 401 during this tab's own renewal ends the sign-in and revokes the fresh token.
    - Seen mechanically: in finding 3's first variant, /revoke ghu_TAB2 follows a renewal that
      succeeded.
    - When it would harm: only where GitHub refuses a token that the refresh would have replaced.
      That happens with a clock moved by more than a minute within the eight hours. It would also
      happen if GitHub revokes the old user token when its refresh token is spent, because a slow
      call with the old token would then reach GitHub after the renewal. That GitHub behaviour could
      not be checked here (no network beyond the local server).
    - Fix: while `refreshing` is set, refusedToken() waits for the renewal and retries with the
      renewed token.

T3. The window between another tab's write and this tab's follow.
    - Claim: the window is 300 ms plus one /user round trip. A write pressed in it goes out as the
      new account before the page names it, even with fixes 4 and 5. R2d's later offsets show calls
      with the new token before the name changed.
    - Fix: one rule in gh() for every non-GET would close findings 1, 3 (the task) and 2 (its
      writes) and this window. Send only when the token about to be sent equals shownToken.
      Otherwise ask /user first and stop on a changed login.

T4. The sign-in box stands on the page while a stored sign-in is checked or renewed.
    - Findings 5 (R2a) and 6 (R10) both start there.
    - A "Checking your sign-in..." state in its place would close both windows. It would also stop
      a press of Sign in with GitHub mid-renewal, which can leave a spent refresh token stored.

T5. storeSignin() removes the old keys before it sets the new one.
    - Another tab cannot see the gap in practice, because its look waits 300 ms.
    - But where setItem throws (a full localStorage), three things go wrong together. The kept
      sign-in is removed and its token revoked. This tab works on a token held only in memory. The
      other tabs say "forgotten in another tab, or GitHub refused it there".

T6. A renewal cut off after the service has spent the refresh token leaves the spent token stored.
    - Examples: the tab holding the renewal turn closes, or the page navigates to GitHub's sign-in.
    - Effect: the next tab is refused and signs every tab out.
    - This comes with single-use refresh tokens and cannot be fixed in the page alone.

Noted, not a finding: Forget's sentence sends a pasted token to
github.com/settings/personal-access-tokens. That page holds fine-grained tokens; a classic token
(ghp_) is deleted at github.com/settings/tokens. The box asks for a fine-grained token, but it
accepts any.
